# Рунбук: uptime за месяц (стори 10.7, AC-04)

**Статус документа.** AC-04 («uptime за месяц ≥ 99%») — ОПЕРАЦИОННЫЙ пункт,
автотестом **не проверяется** (D-10.7-8). Uptime — измерение извне за
календарный период; тест живёт секунды и измеряет другое. Внешнего
мониторинга нет: NFR65 прямо запрещает APM в MVP.

**Чего probe НЕ делает (говорим прямо).** `health-probe` (стори 10.7) —
не монитор доступности. Он опрашивает `/health/deep` раз в минуту и молчит,
пока сервис отвечает. Из этого следует:

- probe **не измеряет uptime** и не считает проценты — он не хранит историю;
- при лежащем api probe жив (он отдельный контейнер) и ушлёт алерт — но
  **при лежащем ХОСТЕ его не увидит никто**: и probe, и api, и бот-канал
  живут на одной машине;
- «сервис отвечает» ≠ «сервис работает»: 200 на health при сломанной
  бизнес-логике probe считает успехом.

Поэтому источник uptime ниже — **журнал алертов probe + ручная сверка**, и
это честно названо приближением, а не мониторингом.

**Связанный долг: W-10.7-b** — внешний монитор как независимый источник
(перед публичным запуском). До его появления AC-04 закрыт частично.

---

## 1. Порог

| Показатель | Значение |
|---|---|
| Целевой uptime за календарный месяц | **≥ 99%** |
| Допустимый простой | **≤ 7 ч 12 мин** в месяц (0,01 × 30 × 24 ч) |
| Допустимый простой в сутках (справочно) | ≤ 14 мин 24 с |

**Почему 99%, а не 99,9%.** Пилот на одном узле без резервирования: 99,9%
(≤ 43 мин в месяц) требует отказоустойчивости, которой нет (ADR-14 — один
VPS, `restart: unless-stopped`, без второй ноды). Обещать 99,9% на такой
архитектуре — обещание, которое нельзя выполнить.

## 2. Источник данных (приближённый)

1. **Журнал алертов probe** — сообщения бота за месяц. Каждое сообщение
   содержит `env`, `check`, `count`/`error_type`, `duration_ms`.
2. **Журнал контейнеров** — `docker compose ps` и `docker events` за период
   (если включён `json-file` с ротацией). Рестарт контейнера без алерта —
   тоже простой, и его видно только здесь.
3. **Ручной журнал инцидентов** — записи владельца («в 14:20 хост
   перезагружался 6 минут»). Это единственный источник для случаев, когда
   лежал весь хост.

**Порядок сбора.** Начало месяца — зафиксировать дату; конец месяца —
выгрузить сообщения бота за период и свести с журналом инцидентов.

## 3. Форма месячного отчёта

Заполняется в конце календарного месяца, до 3-го числа следующего.

| Поле | Значение |
|---|---|
| Месяц |  |
| Всего минут в месяце |  |
| Минут простоя (сумма инцидентов) |  |
| Uptime, % |  |
| Порог ≥ 99% выполнен | да / нет |
| Инциденты (дата, длительность, причина) |  |
| Что сделано, чтобы не повторилось |  |
| Источник(и) данных | журнал алертов / `docker events` / ручной журнал |

**Правило расчёта.** `uptime = (всего_минут − минуты_простоя) / всего_минут
× 100`. Минуты простоя суммируются по инцидентам; пересекающиеся интервалы
считаются один раз (иначе двойной учёт занижает uptime).

## 4. Если порог не выполнен

1. Зафиксировать инциденты в отчёте — не «округлить» до 99%.
2. Классифицировать причину: хост / контейнер / БД / внешняя зависимость.
3. Если причина — отсутствие резервирования (а не разовый сбой), это
   аргумент к W-10.7-b (внешний монитор) и к решению о второй ноде; решает
   владелец, не дежурный.
4. Люфт «чуть ниже 99%» не считается выполнением: порог — граница, а не
   ориентир.

## 5. Границы

- Внешний монитор не внедряется (NFR65) — W-10.7-b вынесен за MVP.
- uptime кодом не измеряется: `pilot_metrics_service` (10.5) — источник
  NFR1–NFR6 (продуктовые метрики пилота), а не NFR15.
- Probe не заменяет мониторинг; см. оговорку выше.
