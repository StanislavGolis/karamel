Что было сделано до регистрации: маршрут `GET /api/health` реализован и покрыт

«Монитор настроен» в этом документе означает «зарегистрирован и прислал
успешные проверки», а не «мы решили его поставить». Первая серия измерений —
три подряд `200` после восстановления 2026-10-27 (§2).

Это **единственное исключение** из `NFR65` («полноценный APM не внедряется»),
оговорка к которому - в `prd-v2-action-first.md:858-866`.

**Что именно проверяет монитор.** Только «процесс web отвечает и видит api»:
маршрут `apps/web/src/app/api/health/route.ts` делает один `GET {API_URL}/health`
и отдаёт `200 {"status":"ok"}` либо `503 {"status":"unavailable"}`. Он **не**
смотрит БД, **не** читает бизнес-логику, **не** заменяет probe и
`/health/deep`.

**Чего probe НЕ делает (говорим прямо).** `health-probe` (стори 10.7) —
не монитор доступности. Он опрашивает `/health/deep` раз в минуту и молчит,
пока сервис отвечает. Из этого следует:

- probe **не измеряет uptime** и не считает проценты — он не хранит историю;
- при лежащем api probe жив (он отдельный контейнер) и ушлёт алерт — но
  **при лежащем ХОСТЕ его не увидит никто**: и probe, и api, и бот-канал
  живут на одной машине;
- «сервис отвечает» ≠ «сервис работает»: 200 на health при сломанной
  бизнес-логике probe считает успехом.

Поэтому источник uptime ниже — **журнал UptimeRobot** (внешний, видит хост
снаружи), а журнал probe — вспомогательный.

## 1. Порог

| Показатель | Значение |
|---|---|
| Целевой uptime за календарный месяц | **≥ 99%** |
| Допустимый простой | **≤ 7 ч 12 мин** в месяц (0,01 × 30 × 24 ч) |
| Допустимый простой в сутках (справочно) | ≤ 14 мин 24 с |

**Почему 99%, а не 99,9%.** Пилот на одном узле без резервирования: 99,9%
(≤ 43 мин в месяц) требует отказоустойчивости, которой нет (ADR-14 — один
VPS, `restart: unless-stopped`, без второй ноды). Обещать 99,9% на такой
архитектуре — обещание, которое нельзя выполнить.

## 2. Источник данных

**Адрес монитора.** `https://www.xn--j1accp.xn--p1ai/api/health` (домен стенда
`крмл.рф`; в punycode — `xn--j1accp.xn--p1ai`). Проверено замером 2026-10-27:
`/` → 200, `/api/health` → 404 до правки (маршрута не было), `via: 1.1 Caddy`.

> ⚠️ **Не путать с `карамель.рф`.** Этот домен резолвится в `95.163.244.136`
> и отвечает `server: openresty` с `x-cache-status` — это **не** стенд
> (`129.101.113.246`). Монитор на `карамель.рф/api/health` получает `403` и
> измеряет чужой сервер. Домен стенда на 2026-10-27 — `www.xn--j1accp.xn--p1ai`
> (`WEB_ORIGIN` в `.env` стенда).

**Каким методом опрашивать.** `HEAD` **или** `GET` — оба возвращают корректный
статус-код. Замерено на прод-сборке 2026-10-27:

| Состояние api | `HEAD /api/health` |
|---|---|
| api жив | **`200`** |
| api мёртв | **`503`** |

Лог при мёртвом api: `[api/health] запрос к api не удался: fetch failed` /
`HEAD /api/health 503 in 17ms`. `HEAD` работает так же, как `GET`: тот же
статус-код без тела, а UptimeRobot смотрит именно код ответа. Бесплатный тариф
навязывает `HEAD` — это рабочий вариант, **не дефект** и не причина красного
монитора.

> Прежняя редакция этого абзаца утверждала обратное («Next ответит `405`,
> монитор будет красным всегда»). Это была **догадка вместо замера**, а не факт;
> долг `W-11.2-p`.

Адрес — без трейлинг-слэша: `/api/health/` со слэшем отдаёт `308` (проверено на
прод-сервере 2026-10-27), а маршрут трактует 3xx как недоступность.


**Источники, по приоритету.**

1. **Журнал UptimeRobot** — основной источник. Что выгружать: `% uptime` за
   период, список инцидентов с длительностью, дата/время в TZ стенда.
   **TZ стенда уточнить на месте** (CR 2026-10-27: `grep 'Asia/|TZ='` по
   `.env`, `.env.example`, `docker-compose.yml` даёт 0 совпадений — прежнее
   `Asia/Tomsk` было догадкой; часовой пояс берётся из `date`/панели, а не по
   памяти). Живёт на стороне сервиса, поэтому видит падение
   всего хоста — то, чего probe увидеть не может.
2. **Журнал алертов probe** — сообщения бота за месяц. Каждое сообщение
   содержит `env`, `check`, `count`/`error_type`, `duration_ms`. Пометка,
   которую нельзя опускать: **живёт на той же машине, что и api — падение
   хоста он не видит**. Годится для сверки «внутренняя деградация без
   внешнего отказа».
3. **Журнал контейнеров** — `docker compose ps` и `docker events` за период
   (если включён `json-file` с ротацией). Рестарт контейнера без алерта —
   тоже простой, и его видно только здесь.
4. **Ручной журнал инцидентов** — записи владельца («в 14:20 хост
   перезагружался 6 минут»).

**Порядок сбора.** Начало месяца — зафиксировать дату; конец месяца —
выгрузить отчёт из UptimeRobot за период, сверить с журналом probe и ручным
журналом, спорные интервалы записать как инциденты.

### Процедура месячной выгрузки из UptimeRobot

1. Войти в панель UptimeRobot → **Monitors** → выбрать монитор
   `karamel api health` (имя задаётся при создании; тип HTTP(s), интервал 300 с).
2. Открыть вкладку **Stats / Log** выбранного монитора.
3. Задать период: **Custom range** — первое и последнее число календарного
   месяца (не «последние 30 дней»: отчёт считается за календарный месяц).
4. Снять два числа и список событий:
   - **Uptime ratio** за период (процент) — переносится в отчёт как есть;
   - **Downtime events**: начало, конец, длительность каждого.
5. Зафиксировать TZ: панель показывает время в TZ аккаунта. TZ стенда узнать
   командой `date +%Z%z` на стенде (не по памяти) и пересчитать время
   инцидентов **до** записи в отчёт. Обе зоны записать в §3 рядом с периодом.
6. Перенести в §3. **Правило расчёта не меняется** (Task 6.4): знаменатель —
   все минуты календарного месяца, по формуле §3. Периоды, когда монитор не
   работал, **не** изымаются из знаменателя: иначе «99%» достигается
   исключением неудобных дней, а не работой сервиса. Если период не покрыт
   журналом, он вносится как инцидент с причиной «нет данных» — не как
   отсутствие простоя.

## 3. Форма месячного отчёта

Заполняется в конце календарного месяца, до 3-го числа следующего.

| Поле | Значение |
|---|---|
| Месяц |  |
| Всего минут в месяце |  |
| Минут простоя (сумма инцидентов) |  |
| Uptime, % |  |
| Порог ≥ 99% выполнен | да / нет |
| Инциденты (дата, длительность, причина) |  |
| Что сделано, чтобы не повторилось |  |
| **Источник(и) данных** | **`UptimeRobot`** (основной) / журнал probe / `docker events` / ручной журнал |

**Правило расчёта.** `uptime = (всего_минут − минуты_простоя) / всего_минут
× 100`. Минуты простоя суммируются по инцидентам; пересекающиеся интервалы
считаются один раз (иначе двойной учёт занижает uptime).

**Значение поля «Источник(и) данных».** Основным указывается `UptimeRobot`:
это единственный источник, который видит отказ хоста. Журнал probe
дописывается через `/` только там, где он дал интервал, которого нет во
внешнем журнале.

## 4. Если порог не выполнен

1. Зафиксировать инциденты в отчёте — не «округлить» до 99%.
2. Классифицировать причину: хост / контейнер / БД / внешняя зависимость.
3. Если причина — отсутствие резервирования (а не разовый сбой), это
   аргумент к решению о второй ноде; решает владелец, не дежурный.
4. Люфт «чуть ниже 99%» не считается выполнением: порог — граница, а не
   ориентир.

## 5. Границы

- Монитор видит только «процесс web отвечает и видит api». Он **не видит**
  бизнес-логику: 200 на `/api/health` совместим со сломанной оплатой,
  пустой лентой и любым дефектом домена.
- Монитор **не заменяет probe** и не заменяет `/health/deep`: probe
  проверяет БД и Redis изнутри, монитор — только внешнюю доступность.
- Монитор **не является частью продукта**: это внешний сервис, он не входит
  в compose, не пишет в нашу БД, не получает персональных данных и удаляется
  одной командой (§6). Если он удалён — источник uptime исчезает, и §2
  откатывается к probe + ручному журналу (то есть к приближению).
- uptime кодом не измеряется: `pilot_metrics_service` (10.5) — источник
  NFR1–NFR6 (продуктовые метрики пилота), а не NFR15.
- Probe не заменяет мониторинг; см. оговорку в шапке.

## 6. Как удалить монитор

Исключение из `NFR65` действует, только пока монитор удаляется одной командой
(условие 4 оговорки). Ключ API **в репозиторий не попадает** (D-11.2-5):
в командах ниже — переменная окружения `$UPTIME_API_KEY`, значение берётся
в панели UptimeRobot → **My Settings → API Settings → Read/Write API Key**
и живёт только в окружении дежурного.

**Способ (а) — панель, 2 клика.** Monitors → выбрать монитор → **Delete** →
подтвердить. Годится, когда под рукой браузер.

**Способ (б) — одна команда, без панели.**

```bash
# Ключ — только в окружении дежурного, не в репозитории и не в истории shell:
read -rs UPTIME_API_KEY && export UPTIME_API_KEY

# Найти id (и убедиться, что удаляем тот монитор):
./scripts/uptime/delete-monitor.sh            # без аргумента печатает usage и id не трогает
curl -s -X POST https://api.uptimerobot.com/v2/getMonitors \
  -H 'Content-Type: application/json' \
  -d "{\"api_key\":\"$UPTIME_API_KEY\",\"format\":\"json\"}" \
  | python3 -c 'import json,sys; [print(m["id"], m["friendly_name"], m["url"], sep="\t") for m in json.load(sys.stdin)["monitors"]]'

# Удалить по id — команда сама проверяет эффект и возвращает код выхода:
./scripts/uptime/delete-monitor.sh <ID>
```

**Почему скрипт, а не строка `curl` в документе.** До CR 2026-10-27 здесь
стоял `editMonitor` со `status:0` — это **пауза**, а не удаление: запись
остаётся в аккаунте и возвращается в `getMonitors`, то есть собственная
проверка рунбука пройти не могла. Команда, которую нельзя проверить
исполнением, — не «удаление одной командой».

`scripts/uptime/delete-monitor.sh` делает три вещи и падает громко:

| Код | Что значит |
|---|---|
| `0` | `deleteMonitor` подтвердил удаление, и `getMonitors` больше не содержит `id` |
| `1` | удаление **не подтверждено** — `id` всё ещё в аккаунте (например, кто-то вернул `editMonitor`) |
| `2` | нет ключа/id или API ответил ошибкой — вызов не состоялся |

Удаление идёт методом **`deleteMonitor`** (`id` — число, не строка). `status:0`
в UptimeRobot API v2 — пауза; пока монитор на паузе, он остаётся в аккаунте,
и условие 4 оговорки не выполнено.

**Проверка, что удаление сработало** — не отдельный ручной шаг, а часть
команды: скрипт возвращает `0` только когда `getMonitors` уже не содержит
этого `id`. Дополнительно: `https://www.xn--j1accp.xn--p1ai/api/health`
продолжает отвечать 200 (маршрут остаётся — он часть продукта, а не монитора).

**Проверено на живом аккаунте — 2026-10-27 (долг `W-11.2-b` закрыт).**

До этой даты здесь стояла оговорка: «живой UptimeRobot не вызывался, ключа
у проекта нет; если бесплатный тариф не даёт `deleteMonitor`, это выяснится
при `W-11.2-b`». Выяснено замером, а не догадкой:

| Шаг | Замер | Результат |
|---|---|---|
| `getAccountDetails` | `stat: ok`, `active_subscription: null` | тариф **бесплатный**, `monitor_limit: 50` |
| `newMonitor` временный (`example.com`) | `stat: ok`, `id 804437459` | создание доступно |
| `delete-monitor.sh 804437459` | код выхода **`0`** | `deleteMonitor` **есть на free-тарифе** |
| `getMonitors` после | `total: 1` | в аккаунте остался только боевой `804437010` |

**Вывод.** Условие 4 оговорки к `NFR65` («удаляется одной командой»)
**выполнено на бесплатном тарифе**. Переформулировать оговорку не нужно.

Наблюдения по аккаунту, полезные при эксплуатации:

- `monitor_interval: 5` мин — минимальный интервал тарифа. Наш `interval: 300`
  секунд стоит ровно в него, **уменьшать нельзя**.
- `monitor_limit: 50` при `total_monitors_count: 1` — запас велик, но
  временные мониторы всё равно удалять сразу (условие 4).
- `deleteMonitor` принимает `id` числом. Временный монитор удаляется той же
  командой, что и боевой, — отдельной процедуры для «тестового» нет.

**Про доказательство тестом.** Тест
`apps/web/src/app/api/health/__tests__/runbook-command.test.ts` против
стаб-сервера (воспроизводит разницу `deleteMonitor` / `editMonitor`) остаётся
регрессионной защитой: он ловит возврат к `editMonitor status:0` в самом
скрипте. Живой замер доказывает, что тариф не блокирует вызов; тест
доказывает, что скрипт продолжает вызывать правильный метод.

**Что удаление НЕ ломает.** Маршрут `/api/health` и код web остаются: они
полезны сами по себе (healthcheck, ручная проверка) и не являются частью
исключения. Исключение — только внешний сервис.
