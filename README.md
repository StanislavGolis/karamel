# Карамель — дейтинг по событиям (Action-first dating)

> Не лента анкет, а карточка конкретной встречи: «иду в кино в пятницу, ищу компанию».

Обычный дейтинг начинается с внешности и бесконечного свайпа. Здесь — наоборот:
сначала совместное действие в реальном мире, потом знакомство. Переписка
открывается только после того, как компания собралась.

---

## Как это устроено

**Единица показа — карточка события.** Человек публикует: что, когда, где, сколько
человек ищет, до какого момента принимает заявки. Место — ссылка на проверенную
точку города (`places`), а не свободный текст и не координаты.

**Два режима набора.** Открытый набор — присоединяйся сразу. Режим заявок —
кандидат пишет сообщение, автор выбирает участников сам.

**Чат — следствие, а не вход.** Один чат на карточку (`UNIQUE event_card_id` в БД).
Пока компания не собрана, переписки не существует: состав вычисляется из
подтверждённых заявок и не может «разойтись» с реальностью.

**Дефицит как механика.** У карточки вместимость 1–6 и окно решения; у автора лимит
активных карточек, у заявителя — лимит активных заявок. Отсюда конкуренция за место
и требование корректной работы с гонками на уровне БД.

**Явка фиксируется поимённо.** После встречи — отметки «пришёл / не пришёл» по каждой
паре «автор ↔ участник», а не агрегат по карточке. Иначе нельзя ни разобрать жалобу,
ни показать историю.

## Приватность и безопасность

| Что | Как |
|---|---|
| Переписка | **AES-256-GCM** на уровне приложения, ключ вне БД; AAD привязан к домену и отправителю |
| Геолокация | **Координаты не хранятся нигде** — место хранится ссылкой на проверенную точку |
| Данные и медиа | Дата-центры РФ, **152-ФЗ** |
| Вход | Яндекс ID, VK ID (OAuth + PKCE), SMS-код |
| Модерация | Очередь фото (`pending → approved/rejected`), жалобы, санкции: предупреждение и бан |

## Инженерные решения

**Миграции отдельным сервисом.** `migrate` применяет схему и завершается, API ждёт его
через `depends_on: condition: service_completed_successfully`. Рестарт контейнера не
меняет схему молча.

**Статусы — `text` + `CHECK`, не PG-enum.** `ALTER TYPE ... ADD VALUE` не откатывается
в транзакции; миграция на `CHECK` переписывает одно ограничение и откатывается целиком.

**Инварианты живут в БД, а не в соглашениях.** Уникальность чата на карточку —
`UNIQUE`; частичная уникальность заявки — только по «занимающим» статусам, чтобы
после отмены можно было подать снова.

**Производные состояния считаются, а не хранятся.** Статус явки выводится из пары
флагов — в Python и в SQL `CASE` для атомарного `UPDATE ... RETURNING`; третье
представление (`CHECK`) стережёт инвариант для вставок сырым SQL. Расхождение любого
из трёх — красный тест.

**Геокодер без утечки координат.** Адрес ищется и нормализуется, но точные координаты
не пишутся ни в БД, ни в логи — это проверяется отдельным тестом
(`test_address_coordinates_not_logged`).

## Локальный запуск

```bash
cp .env.example .env
docker compose up --build
curl localhost:8000/health   # {"status":"ok"}
```

Порты привязаны к `127.0.0.1` — снаружи БД и Redis недоступны.

### Без Docker

```bash
cd services/api
python -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/uvicorn app.main:app --reload

cd apps/web && npm ci && npm run dev
```

## Тесты

```bash
cd services/api && pytest        # API: unit + integration
cd apps/web && npm test          # Web: vitest
```
